# چارچوب کمی‌سازی E-E-A-T برای صفحات وب فارسی

پروژه Proof of Concept برای استخراج و کمی‌سازی شاخص‌های E-E-A-T
(Experience, Expertise, Authoritativeness, Trustworthiness) از صفحات وب فارسی.

## معماری

```
URL ورودی
  |
  v
[Fetcher]      -> دانلود HTML خام
  |
  v
[Parser]       -> تبدیل HTML به ساختار DOM قابل پردازش
  |
  v
[Extractors]   -> استخراج ۱۹ شاخص در ۴ دسته (Experience, Expertise, Authority, Trust)
  |
  v
[Normalizer]   -> نرمال‌سازی شاخص‌ها به بازه [۰,۱]
  |
  v
[Scorer]       -> میانگین ساده شاخص‌ها در هر مؤلفه -> ترکیب وزنی ۴ مؤلفه -> امتیاز نهایی
  |
  v
[Reporter]     -> خروجی JSON / CSV
```

مرجع کامل شاخص‌ها، فرمول‌ها و منابع: فایل `feature_dictionary_v3.md` (جدا از این پروژه).

## نصب

```bash
pip install -r requirements.txt
```

نصب پکیج پایتونی `playwright` به‌تنهایی کافی نیست؛ خودِ مرورگر
(Chromium headless) که Playwright برای رندر صفحات جاوااسکریپتی
(مثل Next.js/React) استفاده می‌کند، باید جداگانه نصب شود:

```bash
python -m playwright install chromium
```

بدون این مرحله، هر تلاش برای رندر یک صفحه‌ی JS-rendered (چه به‌صورت
خودکار — تشخیص heuristic در fetcher — و چه با `--render-js`) با خطای
«Executable doesn't exist» شکست می‌خورد؛ به‌لطف مدیریت خطای موجود در
`fetcher/page_downloader.py`، این شکست برنامه را کرش نمی‌دهد اما
یعنی صفحه فقط با HTML خام (بدون اجرای جاوااسکریپت) تحلیل می‌شود.

## ساختار پوشه‌ها

- `fetcher/`       دانلود HTML از URL
- `parser/`        پارس HTML به DOM
- `extractors/`    ۴ ماژول استخراج شاخص (یکی برای هر مؤلفه E-E-A-T)
- `normalization/` نرمال‌سازی شاخص‌های خام
- `scoring/`       ترکیب وزنی و محاسبه امتیاز نهایی
- `reporting/`     تولید خروجی نهایی
- `config/`        فایل‌های وزن‌دهی (weights_equal.yaml, weights_ahp.yaml)
- `utils/`         توابع کمکی مشترک (تاریخ شمسی، تحلیل دامنه، و غیره)
- `data/`          نمونه URL های ورودی برای فاز ارزیابی
- `tests/`         تست واحد برای هر ماژول
- `webapp/`        رابط وب (Flask) برای اجرای تعاملی چارچوب

## گزارش PDF

صفحه‌ی نتیجه در وب‌اپ یک دکمه‌ی «دانلود گزارش کامل (PDF)» دارد. این
گزارش شامل امتیاز نهایی، خلاصه‌ی ۴ مؤلفه، و برای هر یک از ۱۹ شاخص:
دلیل نمره (evidence) و یک توصیه‌ی بهبود مشخص — حتی برای شاخص‌هایی که
وضعیت خوبی دارند (با لحن «برای حفظ این نتیجه»). ساخت PDF با
`reportlab` و فونت فارسی `Vazirmatn` (در `webapp/static/fonts/`، مجوز
SIL Open Font License) انجام می‌شود؛ `arabic-reshaper` و `python-bidi`
حروف فارسی را برای نمایش صحیح (اتصال حروف + راست‌به‌چپ) آماده می‌کنند.
اگر ساخت PDF به هر دلیلی شکست بخورد، فقط دکمه‌ی دانلود مخفی می‌شود —
خودِ صفحه‌ی نتیجه هرگز به همین دلیل خراب نمی‌شود.

## مقایسه‌ی دو صفحه

در صفحه‌ی اصلی وب‌اپ، بالای فرم یک انتخاب‌گر هست: «تحلیل یک صفحه»
(حالت پیش‌فرض، دقیقاً همان رفتار قبلی) یا «مقایسه‌ی دو صفحه». فقط در
حالت مقایسه فیلد آدرس دوم نشان داده می‌شود. نتیجه در مسیر `/compare`
(قالب `webapp/templates/compare.html`) نمایش داده می‌شود: امتیاز نهایی هر
دو صفحه، ۴ مؤلفه و هر ۱۹ شاخص (مقدار هر طرف، اختلاف، و برنده).

- منطق برنده یک تابع خالص جداگانه است: `decide_winner` در
  `webapp/comparison.py` (تست واحد: `tests/test_compare.py`). مقایسه روی
  درصد گردشده‌ی نمایش‌داده‌شده انجام می‌شود. اگر درصدها برابر باشند «مساوی»؛
  اگر یکی از دو طرف «داده کافی نیست» یا «غیرقابل‌اعمال» باشد «بدون قضاوت»؛
  در هر دو حالت برنده‌ای اعلام نمی‌شود.
- هر دو صفحه با همان `process_single_url` و `build_report_context` موجود
  تحلیل می‌شوند (کد کپی نشده) و پشت‌سرهم (نه هم‌زمان) دریافت می‌شوند.
- اگر دریافت یکی از دو صفحه شکست بخورد، پیام می‌گوید کدام آدرس مشکل
  دارد. اگر دو آدرس یکسان باشند، هشدار داده می‌شود و تحلیلی انجام نمی‌شود.
- PDF مقایسه در `/download-compare-pdf/<token>` با همان کش و همان سقف
  ۳۰ فایل PDF تک‌صفحه ساخته می‌شود (تابع `generate_comparison_pdf` در
  `reporting/pdf_report.py`). برای هر شاخص دلیل نمره‌ی هر دو طرف آمده و
  توصیه‌ی «برای بهبود» برای طرف ضعیف‌تر. اگر ساخت PDF شکست بخورد، فقط
  دکمه‌ی دانلود پنهان می‌شود.
- ⚠️ هم در صفحه‌ی مقایسه و هم در PDF صریحاً نوشته می‌شود: اختلاف امتیاز
  معنی آماری ندارد و فقط تفاوت شاخص‌های همین ابزار را نشان می‌دهد.

## ظاهر رابط وب

رابط وب با جهت «گزارش تحلیلی چاپی» طراحی شده (`webapp/static/style.css` و
قالب‌های `webapp/templates/`). هیچ منطق امتیازدهی یا استخراجی تغییر نکرده است.

- **ترتیب صفحه‌ی نتیجه:** خلاصه و آدرس صفحه ← امتیاز نهایی ← چهار مؤلفه ←
  جزئیات شاخص‌ها ← معنی وضعیت‌ها. یک ستون با عرض ثابت، یک عنوان اصلی، عنوان
  بخش‌ها هم‌اندازه، یک دکمه‌ی اصلی (پر) و دکمه‌های فرعی (خطی).

- **پالت:** `#F5F2EB` کاغذ، `#FFFFFF` سطح، `#29352F` متن، `#34443D` رنگ اصلی،
  `#718477` نوارها، `#B77953` تأکید، `#DCDDD5` خطوط. فقط سه رنگ مشتق‌شده
  برای خوانایی و معنای وضعیت اضافه شده: `#4B5951` (متن فرعی)، `#8A5232`
  (همان رنگ تأکیدی، تیره‌تر، فقط برای متن کوچک) و `#8F3B2E` (وضعیت «ضعیف»).
- **وضعیت‌ها با شکل و واژه** معنی می‌شوند، نه فقط رنگ: دایره‌ی پر = خوب،
  نیم‌پر = نیاز به بهبود، حلقه = ضعیف یا صفر، حلقه‌ی خط‌چین = داده ناموجود،
  خط کوتاه = غیرقابل اعمال. «امتیاز صفر» نوار خالیِ دارای آستانه است؛ «داده
  ناموجود» نوار خط‌چین و «غیرقابل اعمال» خط نازک.
- **آستانه‌های روی نمودارها (۴۰ و ۶۰)** از `webapp/recommendations.py`
  (`IMPROVEMENT_THRESHOLD` و مقدار ۰٫۴ داخل `get_status_level`) می‌آیند و
  `tests/test_ui.py` هم‌خوانی‌شان را با `get_status_level` بررسی می‌کند.
- **فونت:** وزیرمتن به‌صورت فایل محلی (`webapp/static/fonts/*.woff2`، مجوز SIL
  OFL) بارگذاری می‌شود؛ ابزار برای ارائه بدون اینترنت هم همان ظاهر را دارد.
- **حالت «در حال بررسی»** فهرست مراحل واقعی پایپ‌لاین و زمان سپری‌شده را
  نشان می‌دهد؛ پیشرفت هر مرحله جدا گزارش نمی‌شود (تحلیل در یک درخواست
  انجام می‌شود).
- **گزارش PDF** (تک‌صفحه و مقایسه) با همان پالت و همان ترتیب رابط ساخته می‌شود، ولی
  ظاهر چاپی خودش را دارد (جلد با نوار تیره، کارت‌های ۲×۲ مؤلفه‌ها، سرتیتر تیره‌ی
  هر مؤلفه، ردیف‌های سفید شاخص‌ها؛ اعداد و نتیجه دقیقاً همان صفحه‌ی وب است):
  عنوان و آدرس صفحه ← امتیاز نهایی ← چهار مؤلفه ← جزئیات شاخص‌ها (به‌تفکیک
  مؤلفه، با امتیاز و وضعیت و «چرا این نمره» و «برای بهبود») ← معنی وضعیت‌ها.
  فرمت دیگری (مثل CSV یا JSON) برای دانلود در وب وجود ندارد؛ `reporting/reporter.py`
  فقط برای اسکریپت‌های ارزیابی است. هیچ داده‌ای در PDF ساخته نمی‌شود؛ همه از همان
  زمینه‌ی صفحه‌ی نتیجه می‌آید و منطق امتیازدهی تغییر نکرده است.

## نوع صفحه: ویدیومحور (مثل آپارات) و محصول

صفحه‌ی محصول (نشانه‌ی صریح خرید) هم مثل ویدیو چند شاخص نامرتبط (E2، X3، X5) را «غیرقابل اعمال» می‌کند؛ جدول کامل در `feature_dictionary_v3.md`. اگر محتوای اصلی صفحه ویدیو باشد و متنش کوتاه (کمتر از ۲۰۰ کلمه)، شش شاخص متن‌محور (E1، E2، E4، X3، X4، X5) «غیرقابل اعمال» می‌شوند و وزنشان به‌نسبت بین بقیه‌ی شاخص‌ها پخش می‌شود؛ جزئیات و جدول وزن‌ها در `feature_dictionary_v3.md`. گزارش وب و PDF این را صریح می‌گویند.

## اعتبارسنجی با داور انسانی (وب)

صفحه‌ی `/validation`: برگه‌ی نمره‌دهی کور می‌سازد، اسپیرمن با فاصله‌ی اطمینان و نمودار حساب می‌کند و پیش‌نویس متن نتایج می‌دهد. نمره‌دهی انسانی با خود شماست. جزئیات و محدودیت‌ها در `feature_dictionary_v3.md`.

## وضعیت فعلی

همه‌ی ماژول‌ها (fetcher, parser, extractors, normalization, scoring,
reporting, webapp) پیاده‌سازی شده‌اند — این دیگر یک اسکلت خالی نیست.
آستانه‌های عددی شاخص‌ها از `config/settings.yaml` خوانده می‌شوند (نه
ثابت داخل کد)، طبق مقادیر مستندشده در `feature_dictionary_v3.md`.

شاخص T6 (تازگی محتوا) سه منبع تاریخ را به‌ترتیب امتحان می‌کند: JSON-LD
schema، تاریخ شمسی در متن صفحه، و در نهایت (اختیاری) تخمین از Wayback
Machine. این fallback آخر نیازمند دسترسی اینترنت به `archive.org` است
(ممکن است نیاز به فیلترشکن داشته باشد) و با
`external_data_sources.wayback_fallback_for_t6` در `config/settings.yaml`
قابل خاموش‌کردن است؛ اگر شبکه در دسترس نباشد یا خاموش باشد، رفتار
دقیقاً مثل قبل (`is_missing`) است — هیچ‌چیز کرش نمی‌کند.

آنچه بعد از آن باقی می‌ماند، اعتبارسنجی تجربی است: مقایسه‌ی خروجی
چارچوب با داوری انسانی روی نمونه‌ای از صفحات فارسی واقعی. راهنمای
کامل این فاز: `data/rating_rubric.md`. جریان کار:

```bash
python main.py --input data/sample_urls.csv --output results.csv
# نمره‌دهی به همان صفحات طبق data/rating_rubric.md در یک کپی از
# data/human_ratings_template.csv
python validate.py --framework-scores results.csv --human-ratings <فایل نمره‌های شما>
```

⚠️ این اعتبارسنجی با یک داور انجام می‌شود، نه چند داور مستقل — رجوع
به `feature_dictionary_v3.md` بخش «اعتبارسنجی تجربی» برای توضیح کامل
این محدودیت.

## فهرست آدرس‌های اعتبارسنجی (data/urls.csv)

- ۳۲ صفحه‌ی محتوا (نه صفحه‌ی اول سایت) از انواع گوناگون: سایت دولتی و دانشگاهی، خبرگزاری، پورتال خبری، مجله‌ی آموزشی، سایت سلامت، ویرگول، بلاگفا و ویدیوی آپارات.
- انتخاب بر پایه‌ی تنوع نوع سایت بوده، نه بر پایه‌ی کیفیت پیش‌بینی‌شده؛ ستون category فقط نوع سایت را می‌گوید.
- ستون verification می‌گوید هر آدرس چگونه بررسی شد: opened_by_assistant یعنی صفحه باز و خوانده شد؛ seen_in_search_results یعنی آدرس در نتیجه‌ی جستجو دیده شد ولی ابزار خواندن نتوانست آن را باز کند (سایت اجازه نمی‌داد).
- محدودیت: صفحه‌ی محصول (فروشگاهی) در فهرست نیست، چون صفحه‌ی محصول واقعی قابل‌تأیید پیدا نشد. در صورت نیاز خودتان یکی دو نمونه اضافه کنید.
- پیش از نمره‌دادن هر آدرس را در مرورگر باز کنید؛ اگر باز نشد یا محتوا نداشت، ردیفش را حذف کنید.
